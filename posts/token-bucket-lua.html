Rate limiting with a Redis Lua script

Why the obvious INCR/EXPIRE implementation leaks under load, and what atomicity actually buys you.

The version everyone writes first

A fixed window, with INCR and EXPIRE:

n := rdb.Incr(ctx, key)
if n == 1 {
    rdb.Expire(ctx, key, time.Second)
}
if n > limit {
    return false, nil
}

It works, it is short, and it is wrong in two ways that matter.

First, the window boundary. A client can send limit requests at 0.999s and limit more at 1.001s — double the intended rate, twice in a row, every minute. Fixed windows have this shape and no amount of tuning removes it.

Second, and worse for a gateway, it is not atomic. Incr and Expire are two round trips. Under concurrency, several requests can see n == 1 at once and all of them reset the TTL — which means the window never actually expires and the counter grows without bound. Or a request crashes between the two calls and the key becomes a permanent counter with no expiry at all.

Why Lua helps

Redis executes a Lua script as a single unit — nothing else runs against the server while it is in flight. That gives you atomicity without a distributed lock, because the "lock" is Redis itself. 

local key = KEYS[1]
local rate  = tonumber(ARGV[1])
local burst = tonumber(ARGV[2])
local now   = tonumber(ARGV[3])

local b = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(b[1])
local last   = tonumber(b[2])

if tokens == nil then tokens = burst; last = now end

local elapsed = now - last
tokens = math.min(burst, tokens + (elapsed / 1000.0) * rate)

local allowed = true
if tokens < 1 then
    allowed = false
else
    tokens = tokens - 1
end

redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
redis.call('EXPIRE', key, math.ceil(burst / rate) + 10)

if allowed then return {1, 0} end
return {0, math.ceil((1 - tokens) / rate * 1000)}

The script refills the bucket based on real elapsed time rather than on window boundaries, so there is no boundary for a client to straddle. And because it runs atomically, two concurrent requests cannot both observe tokens = 1 and both decide to subtract.

The trade-off worth admitting

Lua scripts are not free — the script is copied to the server on first run and stays in cache, but a long script still blocks the instance while it executes. This one is about 20 lines doing fixed arithmetic and two hash operations, which is short enough not to matter in practice.

The bigger real-world constraint: it holds no lock across network hops, so a failure between HMSET and EXPIRE inside the script is impossible, but a script that could be split into two round trips would reintroduce exactly the race I moved to Lua to remove.

What I built

ratelimit-gateway is a reverse proxy that applies this to an incoming X-API-Key header before forwarding. On rejection it returns 429 with a Retry-After header computed by the script itself — the client is told exactly how long until a token is available rather than being made to guess.
