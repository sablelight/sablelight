Extract the library before you publish the app

A project with nothing worth showing became two independently testable packages. The extraction is the work.

The project started as a Telegram bot. It had 26 source files, 16 of which were indexers for torrent sites. There was no world where that went on a public profile. By every measure I care about — would this embarrass me, is it something I would want an interviewer to open — it was a write-off.

So the first honest question was: what, if anything, in here did I actually write well?

Two files

Out of the whole tree, two things were generic, useful, and had nothing to do with the purpose of the app:

  • config — an option registry where the environment variable name is derived from the key itself.
  • http.go — a shared *http.Client whose transport can be rebuilt at runtime when its proxy setting changes.

Everything else went: the indexers, the aggregation layer, the command handlers, the Dockerfile with the Tor bootstrap in it.

Why it was worth splitting

Inside the app both of those were testable only by simulating an app. As packages they test in isolation — config takes five seconds with t.Setenv, and proxyhttp gets a race-detector test that runs the client from 32 goroutines at once.

The original repository had zero tests. The extracted version has 12, at 92% coverage. Not because I became a better test writer in an afternoon, but because the boundary that made testing awkward was gone.

Two things I had to rename

The config keys were namespaced to the old project — SAKURAS.lookup.proxy_mode. They became proxy.mode, and the env prefix in EnvName() changed to PROXYHTTP_.

The rename was safe for one specific reason I checked before doing it: the env var is derived from the segment after the last dot. So lookup.proxy_mode and SAKURAS.lookup.proxy_mode both resolve to LOOKUP_PROXY_MODE. Changing the namespace did not silently break every deployment's environment.

How to frame it honestly

This is not "I built a proxy library from scratch". It is I extracted the reusable core from a larger service and made it independently testable — which is a normal, common engineering move and a perfectly good thing to say in an interview.

What would have been dishonest is presenting the 400-line library as a project in its own right, as though it had been the goal. It is a component. The stronger portfolio piece is elsewhere.

The lesson I took from it: if you have built one big thing and only part of it is good, you do not have to throw the whole thing away, and you do not have to publish the part that isn't. Find the seam, cut along it, and test the piece you kept.
