One spec, two runtimes: Go stdlib vs FastAPI

The same task API written twice — Go's net/http and Python's FastAPI — where the differences turned out to be.

The spec was small and deliberately boring: create, read, update, delete a task, plus a health check, in-memory storage, thread-safe, with request logging. Roughly what you would write in the first hour of a project.

I wrote it twice rather than reading someone else's comparison. Here is what was actually different when I did it.

Validation is where the philosophy shows

Python's model meant the payload was checked before my handler ran. A missing title was a 422 for free. Roughly four lines of configuration. 

class TaskCreate(BaseModel):
    title: str
    description: str = ""

Go gave no validation at all. I decoded the JSON by hand, checked the field myself, and wrote the 400 myself. More lines, and every endpoint needs the same discipline applied again. Nothing prevents the next person from forgetting.

FastAPI wins this outright for an API-first shape. The Go version is not worse code — it is just code you have to keep writing.

Concurrency was the inverse of what I expected

Go's handler goroutines are concurrent by default; I added a sync.RWMutex to the store and that was the entire story.

FastAPI is a single-threaded event loop. I used async def handlers and an asyncio.Lock. It works, and for an in-memory store it is more than enough — but the default shape of a Python handler is not a concurrent one. You opt into it, and the moment you forget to await a blocking call you block the whole loop.

So: Go was easier to get concurrency right, Python was easier to get the endpoint written. Those are different axes and the usual arguments tend to collapse them into one.

The practical differences

  • Docs: FastAPI generated /docs and /redoc from the same type annotations. Go had none without extra tooling.
  • Dependencies: Go used zero. Python used three (fastapi, uvicorn, pydantic).
  • Race checking: go test -race is built in and caught nothing here, but the confidence cost nothing.
  • Cold start: Go's static binary vs a virtualenv that had to be built first.

What I would actually choose

For a service where the API shape is known up front and I care about deploy shape, Go: no dependency graph, a single binary, race detector available, fewer ways to write something subtly wrong at runtime.

For iterating on an endpoint while the shape is still moving, FastAPI: the automatic docs and model validation mean fewer round trips to check I did not forget a field.

Neither is the correct answer by default, and I do not think either is the more serious language. What this exercise actually taught me was which problems each makes easy — and that you only find that out by writing the same thing twice rather than by arguing it.
