go-redis returns redis.Nil, and redis.Nil == nil

A one-line Go gotcha that broke the build, then broke a test suite in a way I did not expect.

redis.Nil is an error value that means "that key does not exist". It is not the same thing as nil, and Go will happily let you pretend it is. 

val, err := rdb.Get(ctx, "missing").Result()
if err == redis.Nil {
    // key absent — handle it
}
if err != nil {
    return err
}

That is the documented form and it works. The trap is what happens when it slips.

It will not compile if you forget, which is good

When I first hit this I wrote the obvious thing: 

val, err := rdb.Get(ctx, key).Result()
if err != nil {
    return nil, err
}
return val, nil

That compiles. It compiled fine. The problem was not the build at all — it was that Get returns "" for a missing key, and callers were treating an empty string as a legitimate value. No panic, no error, just silently wrong behaviour that only showed up under load.

Where it actually bit me

In the job queue, XReadGroup returns redis.Nil when a consumer group has no new entries — which is the normal case when the queue is empty and the worker is doing its job correctly. My first version treated that as an error and logged it every poll interval: 

streams, err := q.client.XReadGroup(ctx, args).Result()
if err != nil {
    return nil, err   // logs every second when idle
}

It filled a log with 86,400 identical lines a day. Correct-looking code, useless in production.

streams, err := q.client.XReadGroup(ctx, args).Result()
if err == redis.Nil {
    return nil, nil   // idle is not an error
}
if err != nil {
    return nil, err
}

The rule I keep now

  • Missing data is not an error. Handle redis.Nil as its own case.
  • In a poll loop, "nothing to do" is the common case — do not log it as a failure.
  • When a function returns a value and an error, decide explicitly what an empty result means before you ship it.

The job-queue worker now runs quiet when idle, which is the correct behaviour for a background process.
